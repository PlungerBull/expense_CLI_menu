expense world — the terminal supplies the palette

The deferred half of the 2026-07-11 ANSI work. That change made the ground the terminal's own and said, twice, that it did not make the app readable on a light terminal. This page proposes finishing it without the terminal-detection that backlog Phase 8 and decisions.md (2026-08-16) currently commit to: put every colour on an ANSI slot, and let the terminal fill it in. Five picks at the end. Nothing gets written until you pick.

2 · why slots fix it, and what a slot is
The proposal rests on one fact worth seeing before judging anything else. green in a terminal is not a colour — it is slot 2, and the terminal decides what goes in it. Probed from Textual and Rich directly: Color.parse("green") → type=STANDARD, number=2; Color.parse("ansi_default") → Color(0,0,0, ansi=-1) — an opaque fill in the terminal's own colour, not a see-through one. Here is slot 1/2/3 as three real terminals define them:

slot 1 red#dc322f
slot 2 green#859900

The dark profile's green is bright because it has to survive black; both light profiles darken it because it has to survive white. Nobody detected anything — the person who configured the terminal already made this decision, and every other TUI on their machine already honours it. Note also that slot 3 yellow on white is the weakest of the nine; that is the whole reason decision A/B/C exists below.

6 · pick H / I — modals, the only thing that still paints
Two rules paint an opaque non-terminal ground and both break: #modal { background: $panel } (app.tcss:117) — $panel probes to transparent under ANSI, so the modal card would let the list show through it — and the scrim ModalScreen:ansi { background: $background 60% } (app.tcss:104), which probes to Color(0,0,0, a=0.6), i.e. it drops the ANSI marker and becomes plain 60% black. The fix for the card is settled by the probe in §2: ansi_default is an opaque fill in the terminal's own colour, so it hides what is behind while still painting nothing foreign. The scrim is the open half.

8 · what changes, and what does not
What actually changes theme.py: EXPENSE_DARK's ten hexes become ANSI slots on one Theme(ansi=True). resolve_palette gains a removeprefix("ansi_") — Rich rejects Textual's ansi_green spelling but accepts green as slot 2. app.tcss: the Screen:ansi { color: $foreground } pin goes, so text follows the terminal's own foreground; the border and modal rules follow your picks above. What does NOT change The ground — that shipped 2026-07-11 and this builds on it. The cursor row (reverse) and every dim/bold — already terminal-native, ~40 sites, untouched. Account and category swatches — those render the user's own stored hex from the engine, not a theme colour. The flat CLI — monochrome apart from those swatches, and already NO_COLOR-aware. run_world — untouched, which is the entire saving. What this deletes from the plan of record The OSC 11 query, the COLORFGBG fallback, the select() timeout, the luminance calculation, and the second hand-tuned palette. All of it.
Two things stated, not asked — say so if you disagree:
  • This reverses two recorded decisions — the 2026-07-11 seam entry rejected a full native-ANSI theme for "throwing away the tuned sign-color palette", and the 2026-08-16 entry commits to terminal detection. Both get superseded in decisions.md, backlog.md and tui-plan.md with the reversal stated plainly, not quietly edited.
  • The §4 theming principle stands and gets stronger: recolour foreground and semantic spans only, never paint a base surface. Option I honours it absolutely; H keeps one deliberate exception for the modal scrim.

Three things this page did not anticipate All three were found by rendering the app, not by running tests — the suite was green through every one of them. 1. $surface and $panel generate to transparent, not to ansi_default. §5 predicted this for the list border only. It was true of three more: the header rule under the wordmark, and the modal card, which would have been see-through. Structural rules now take $secondary; the card takes a literal ansi_default. 2. The scrim in pane H was silently wiping the screen, not dimming it. §6 reasoned that $background stays ansi_default and so the scrim could keep using it. It does stay — but alpha is dropped on an ANSI colour, so $background 60% resolved to an opaque fill and blanked the list behind the modal: you could not see the row you were confirming a delete on. Fixed with a literal black 60%, which is pick H exactly as its legend described it (the one thing not derived from the terminal, washing toward black on a light ground). Now guarded by test_modal_scrim_dims_rather_than_wipes, which asserts on composited output because the CSS reads correct either way. 3. An ansi=True theme must ship Textual's whole variables block or the app dies at startup on $ansi-background, which its own Screen CSS references. Textual's two ANSI themes fill that block with light- and dark-specific cursor colours — the very split this page refuses. Ours resolves cursors as reverse video instead, matching what CursorList already does in Rich, and correct on any ground by construction. One thing added beyond the picks Footer key glyphs were rendering magenta — Textual's fallback for $footer-key-foreground, a colour this app uses nowhere else. Set to ansi_blue, reading pick D's "help key glyphs" as covering them.
