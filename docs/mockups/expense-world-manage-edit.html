Why Option B is the recommendation
Your stated discomfort was that a fires on any list row. Option B moves a off the list and onto the record you deliberately opened — contextual, not stray — and keeps the enter-never-mutates keymap contract (enter opens a read detail; e edits; a archives). Option A is closer to the original wording (enter → form) but has to solve the "letters type into the input" problem: archive can't be a bare a while the name field is focused, so it becomes a status action-field you cursor to and press ↵ on. Workable, but busier. Both reuse the exact create bar-form for the actual editing.

Fields, per the engine contract
· Account: name + color editable; currency is immutable (PUT rejects it — accounts_cmd.py) → shown read-only. Type/person is not editable (People API unshipped).
· Category: name + color editable.
· Hashtag: name only.

Decisions — resolved 2026-07-07 (shipped)
  1. Model: Option B — enter → read detail; e edit; a archive. Bare a removed from the Manage lists (archive is now contextual to the record you opened).
  2. System categories: e edit is offered — the engine keys them by system_key, not name, so rename/recolor is pipeline-safe and allowed (engine-spec §Categories); supports localization (@Opening → @Apertura). a is hidden — archive/delete deterministically 403 (system category), so suppressing the action reflects engine truth, not a client-invented rule.
  3. Delete: archive-only. The engine 409s deletion of any category with transactions and points at archive, so a delete button would dead-end on exactly the categories you'd want to remove.
