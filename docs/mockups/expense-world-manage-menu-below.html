How they compare
  1. Flavour 1 — on-enter menu. New code = a small menu strip; e reuses the edit form that already exists (still pushed). Cheapest, ships soonest, and it's literally “a menu below the table.” Recommended if you want this landed fast.
  2. Flavour 2 — always-on action bar. Same cost as 1 minus the pushed-vs-not question; the bar is always visible so e/a are self-documenting and the system-lock reads in place. No enter step. Edit still reuses the existing form (pushed).
  3. Flavour 3 — docked edit panel. The nicest — the table never leaves the screen, you edit in the zone. But it needs the bar-form core extracted from a Screen into a mountable widget so it can be docked instead of pushed (a real, though contained, refactor — and it keeps “one copy of everything shared” honest).

The one build note
Flavours 1 & 2 leave the editor as the current pushed bar-form and only add a below-table zone — low risk, mostly new render + a couple of bindings. Flavour 3 is the only one that touches the form: _form.py's FormScreen is a full Screen today; docking it means splitting its guts into a widget both the pushed forms and the docked panel mount. Worth it if “never leave the table” is the goal; skip it if not.

Common to all three
Detail screen deleted · archive is a on the highlighted row (confirm names it) · system categories drop a with a visible reason · same zone appears on Accounts, Categories, Hashtags.

My take
Flavour 2 is the sweet spot: it answers “put a menu below the table” without an enter detour, makes the keys discoverable, and costs almost nothing beyond render because it reuses the existing edit form. Go to Flavour 3 only if you specifically want editing to happen without the screen ever changing — that's the one that earns the refactor. Which flavour, and for edit: keep the pushed form (1/2) or dock it (3)?
