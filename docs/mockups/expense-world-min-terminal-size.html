expense world — minimum terminal size

tui-plan §9 open decision #5, and the last line in backlog Phase 8. The docs record this as already half-answered — "the app degrades rather than refuses, PAGE_ROWS_FLOOR = 5". Measuring it shows that holds down to about 80×22 and no further. Below that it does not degrade, it comes apart, and it never tells you. Two picks at the end. Nothing gets written until you pick.

Two things worth naming. The floor does not do what its comment claims. PAGE_ROWS_FLOOR = 5 guarantees the page holds five rows; it cannot make the viewport show them, so below h≈18 it just guarantees rows are fetched and then clipped. And width has no floor at all — no constant, no clamp, nothing. The column squeeze runs until the data is gone.
3 · pick A / B / C / D — what should it do?
A · refuse at launchoption
$ expense world Error: expense world needs at least 60×20. This terminal is 46×12. $ ▏ (exit code 1)
A size check beside the existing tty guard in run_world. Win: one place, ~4 lines, same shape as the tty check you already have. Cost: refuses to start on a terminal you could still read; says nothing if you shrink the window after launch, which is the more common way to get here.
B · in-app notice screenoption
Terminal too small 46×12 — needs 60×20 Resize and this returns to where you were.
Below the threshold the content is replaced by this; resizing back restores the screen you were on. Win: covers the resize case, explains itself, never loses your place, and the app still starts. Cost: a new screen state to build and test.
C · warn, keep goingoption
◈ EXPENSE WORLD ▸ Transactions ⚠ 46×12 — columns hidden, rows clipped ────────────────────────────────────── ╭─ Ledger … ─╮ │ … -… 2026-… │ │ … -… 2026-… │ ↓ Navigate ⏎ Open
One persistent line; everything else renders as it does today. Win: nothing is taken away — a cramped terminal still shows what fits, and the silence is what gets fixed. Cost: the display is still misleading underneath the warning; the banner costs a line on the screen that has fewest to spare.
D · do nothing, and write the current behaviour down as accepted. Honest option: the terminal is the user's to size, every other TUI degrades similarly, and you have never once hit this in real use. Cost: the failure stays silent, and the docs keep claiming a graceful degradation that stops at 80×22.
4 · pick E / F — where is the line?
Only matters if you pick A, B or C. E · 60×20 — the measured edge of usable. At 60 wide every column still reads; at 20 high all four rows draw. Below this something is actually lost. Cost: 60×20 is already imperfect (the panel's bottom border is gone at h=20), so the threshold blesses a slightly broken render. F · 80×24 — the size the app was designed at, and the classic terminal default. Everything is correct here, with margin. Cost: it would refuse or warn on terminals that genuinely work — a 70×22 window reads fine — so it will fire when nothing is wrong.
Two things stated, not asked — say so if you disagree:
  • Whatever is picked, PAGE_ROWS_FLOOR's comment gets corrected. It claims to prevent clipping "below a <16-line terminal"; it prevents nothing — the rows are fetched and then cut off. That is a wrong comment either way.
  • Height and width both get checked. The width failure has no guard of any kind today and is the sneakier of the two, because the screen looks healthy.

5 · as decided — 2026-08-20, and where this page was wrong
PICKED: D + E. No guard, no refusal, no notice screen — the app degrades silently and that is accepted. Documentation-only change: tui-plan §9 #5 resolved, the PAGE_ROWS_FLOOR comment corrected, a decisions.md entry added with the three rejected shapes. Zero behaviour change.
Two numbers on this page are wrong Re-probing before commit — with a different row count, which is what exposed it — showed the boundary table in §2 was measured too loosely. Kept visible rather than quietly edited, because the entire point of this item was that a claim about degradation went four days unchecked. 1. Width truncation starts at ≈75, not 50. §2 says "80 · 70 · 60 correct". They are not: at w=75 cells already elide, and w=80 is the first width with no ellipsis anywhere. w=50 is where the title becomes a bare … — a later stage of the same failure, not its start. 2. The height threshold is not a constant. §2 says "panel's bottom border lost at h=20". That is true only for a full page. The panel clips when content exceeds the viewport, so it moves with the page size: a 4-row page keeps its border down to h=18, a full 8-row page has already lost it at h=20. The original sweep used 8 rows throughout and read a row-count effect as a height constant. What the docs now say instead 80×24 — everything correct, no truncation, panel closes. Also the size the screens were designed at and the classic terminal default. 60×20 — still workable, already lossy: every row draws, columns ellipsised. Neither is enforced. Pick E was made against the claim "at 60 wide every column still reads", which was false — but since D enforces nothing, the pick only determines which number the docs cite, and both are now cited with what they actually mean.
