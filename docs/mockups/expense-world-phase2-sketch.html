expense world — phase 2 sketch · transfer feature removal · closed 2026-08-16
Everything a user sees change after this phase. Why: the engine deleted its transfer feature on 2026-08-10 — a move between accounts is now recorded as two ordinary transactions (one outflow, one inflow, ordinary categories).
1 · TUI quick-log form — one step shorter, no transfer branch
before — conditional transfer branch
before
Date › Title › Amount › Account › Transfer to? › Category › Hashtags › Note filling "Transfer to?" forked the form: … › Account › Transfer to? › To amount › Note (no category/hashtags on that branch; To amount took a magnitude and auto-set the opposite sign — the sign convention's single sanctioned exception)
submit said "Creating transfer…" · "Transfer created."
after — one straight path
after
Date › Title › Amount › Account › Category › Hashtags › Note no fork, no "TRANSFER TO?" prompt, no auto-signed field — every amount is typed with its explicit sign, everywhere. Category is always asked (the engine now requires it on every transaction).
submit says "Creating transaction…" · "Transaction created."
2 · `expense log` — three flags gone
before
before
$ expense log --title "Wire" --amount -1000 --account-id <id> \ --transfer --to-account-id <id> --to-amount 280 Created: 5555… · Created (transfer leg): 6666…
after — a move = two ordinary entries
after
$ expense log --title "Wire out" --amount -1000 \ --account-id <from> --category-id <cat> $ expense log --title "Wire in" --amount 280 \ --account-id <to> --category-id <cat> --category-id is required on both (no transfer exception)
3 · Error messages — engine speaks, no stale transfer hints
before
before
$ expense transactions batch < move.json Error 422 VALIDATION_ERROR Hint: transfers are not supported in batch creates. Log each transfer individually with 'expense log --transfer …' (update/restore had similar transfer-pair hints)
after — the engine's own words, verbatim
after
$ expense transactions batch < move.json Error 422 VALIDATION_ERROR transactions[0].category_id: Field required the CLI adds no local check and no hint — the engine owns batch validation (user decision 2026-08-16, thin-wrapper rule)
4 · Categories — @Transfer/@Debt rows disappear; hints name @Opening
before
before
Mascotas active @Transfer system 🔒 active @Debt system 🔒 active @Opening system 🔒 active
system categories (@Debt, @Transfer) cannot be modified
after — one system category
after
Mascotas active @Opening system 🔒 active (the engine deleted the other two; existing rows keep their category names in history)
the system category (@Opening) can be renamed but not deleted
5 · Editing — former transfer legs are ordinary transactions now
Old transfer legs stay in the ledger as normal rows. The TUI used to lock amount/account/date when editing a leg (shown faded, skipped); that lock is gone — every field edits like any other transaction, and if something is genuinely locked (completed reconciliation), the engine's 422 says so. Deleting one row of an old pair no longer cascades to its sibling.
Not in this phase: a "move between accounts" convenience (one action that writes the two entries for you) is parked in backlog Phase 8 — it would get its own mockup first.
