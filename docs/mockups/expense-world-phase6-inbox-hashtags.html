expense world — phase 6.1 sketch · tagging a draft · 2026-08-16
Everything repaired so far this month was damage control — the engine deleted things and the app had to stop asking for them. This is the first half of the opposite: the engine gained something on 2026-08-14 and nothing here has offered it to you yet.

What you cannot do today: put a hashtag on an inbox draft. If you capture something quickly and want it tagged #food, you have to promote it into the ledger first and then go back and edit the transaction. Two steps for one thought. Meanwhile the app's own help text has been listing hashtags among the seven fields a draft accepts since Phase 5 — it documents a field it cannot send.

What the engine now does: a draft carries tags from the moment you create it, and promotion carries them into the ledger for you — so the second step disappears rather than moving. Clearing is possible too. None of it breaks anything that works today.

Three things need your pick, at the bottom: what the typed flag is called, whether the typed list grows a column, and whether the app's Inbox list grows one. Nothing gets built until you choose.

3 · decision 1 of 3 — what the option is called
Small, but it is the word you type. Two commands already have this option and both spell it --hashtag-ids. The backlog note, written months ago, said --hashtags. They cannot both be right, and the cost of the mismatch is that you have to remember which command wants which.
A — --hashtag-ids
chosen
inbox add --hashtag-ids inbox update --hashtag-ids transactions --hashtag-ids log --hashtag-ids all four agree. You type the same thing everywhere. Honest about what it wants: you pass ids, not names — names are not accepted anywhere yet.
nothing to relearn, nothing to rename
B — --hashtags, here only
option
inbox add --hashtags inbox update --hashtags transactions --hashtag-ids log --hashtag-ids nicer to type, and it is what the old note said. But two commands now disagree with two others, permanently, for no reason a future reader could reconstruct.
the only option that leaves the app inconsistent with itself
C — --hashtags, everywhere
option
inbox add --hashtags inbox update --hashtags transactions --hashtags log --hashtags consistent AND shorter. Costs a rename of two shipped options. Nothing external depends on the old spelling — no scripts, no other client. If you have typed it into a saved command anywhere, that breaks.
most typing saved; one-time break of your own muscle memory
4 · decision 2 of 3 — does the typed inbox list show tags
Rendered by the app's own table code, so these are real widths, not a drawing. The question is whether tags are worth a column in expense inbox list, and if so where. A draft you have not filled in yet is the thing this list exists to show — the argument for tags is that a tag is often the first thing you know about a purchase and the last thing you remember later.

6 · stated, not asked
· You still cannot create a draft from inside the app. The quick-add form always writes straight to the ledger, so in expense world tagging applies when you edit a draft. Creating one is still a typed command. That gap predates this work and is not part of it — flagging it so the panes above are not read as promising more than they do.

· inbox get will show tags as raw ids, e.g. de37af15-…, because the detail view prints every field verbatim. transactions get does exactly the same today. Making one of them resolve names and not the other would be worse than leaving both; if you want that changed it should be changed for both, as its own small piece of work.

· Nothing here can break an existing draft. The option is optional on create, and on edit an untouched set is left untouched — the app never sends an empty value by accident. That is the engine's contract, and the live check below is what proves the app honours it.

· How this gets verified. The fast test suite cannot see this working — it talks to a written-down imitation of the engine, and the drift checker built last phase is structurally unable to catch a missing field. So 6.1 lands with a real check against the practice database on port 8001, the one that refuses to touch your ledger: create a tag, create a draft carrying it, replace the set, clear it, promote, and assert the tag arrived on the transaction.
Picked 2026-08-16: A + E + H.

A — the option is --hashtag-ids on all four commands. The two new inbox commands copy the two that already exist, so nothing you type today changes, and the word keeps saying what it means: it wants the codes from expense hashtags list, not names. C was rejected because renaming two shipped options buys two characters and, worse, makes the word imply that food would be accepted when the engine still demands the code; B because two commands disagreeing with two others is a puzzle left for whoever reads this next.

E — expense inbox list grows a Tags column at the far right, the same position and the same —-for-empty rule that transactions list already uses. F was rejected on the evidence in its own pane: the Title cell truncates at 24 characters and ate a tag. D was rejected because a tag is often the first thing you know about a draft and the last thing you remember later — worth a column.

H — the Inbox list in expense world grows the same column, positioned before the status marker so the two lists read identically; the card widens from 100 to 110 to match the Transactions screen.

Note for the reader: the typed path is the only one where codes are ever pasted. Inside expense world you pick tags by typing food and choosing from a list — the codes never appear.
