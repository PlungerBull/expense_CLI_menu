expense world — Phase 8 · discoverability

Two open Phase 8 items drawn as one, because they render the same inventory: the ? help overlay and populating the ctrl+p command palette. Audited at HEAD 2026-08-17. Panes tagged REAL are machine-captured; DRAWN panes are proposals built only from keys that exist in source today.

DECIDED 2026-08-17. Three picks are in; §6 is the only pane still awaiting a nod.
  • C — ? opens our own two-column card. Not Textual's panel (A), not one column (B), not a full screen (D).
  • Palette removed entirely — the H/J/K question in §3 is moot and those panes are kept only as the record of what was rejected. See §5 for what removal costs and why it was the cheaper answer than populating.
  • Accept the gap in forms — a focused Input swallows ?, so forms have no help key. No second binding.
1 · what exists today
Two things turned out to be already built, and both change the shape of the work: (a) the Footer already advertises the palette — Textual's Footer renders ^p palette on the right by default (show_command_palette = reactive(True)), so the palette is discoverable but empty of app commands. (b) Textual 8.2.7 ships a built-in keys panel — App.action_show_help_panel + the HelpPanel widget — already reachable via ctrl+p → Keys. So "build a help overlay" is really "curate, or accept Textual's".

5 · decided — the palette is removed, not populated
One line: ENABLE_COMMAND_PALETTE = False on ExpenseApp. The footer hint goes with it for free — Footer.compose gates the ^p palette key on that same flag, so no footer code is touched.

Verified before deciding: nothing in the repo depends on the palette. Two references exist and both are prose — a docstring line in theme.py:15 and a test docstring in test_tui_theme.py:95. Both get reworded in the same commit. And the theme picker it exposes is a picker for a choice we do not offer: THEMES = [EXPENSE_DARK] is one theme, against 21 Textual built-ins we never designed. (Those built-ins do not break the terminal-transparent surface rule — probed at HEAD, screen.background stays ansi=-1 under gruvbox and solarized-light alike, because app.tcss pins the base fill structurally. They are off-brand, not broken. The point stands anyway: it is a menu of 21 wrong answers and 1 right one.)

7 · what gets built
One inventory, one renderer. A single function that, given the active screen, returns its curated key list — the screen's bindings plus the focused widget's, minus Textual's internals, with show=False aliases folded into their partner row. HelpModal renders it as the two-column card. With the palette removed there is no second consumer, so the function stays small and lives next to the modal rather than becoming shared plumbing.

The guard test is the durable half. Every binding in source appears in the inventory, or is on an explicit suppression list — so a binding added later cannot go silently undocumented, which is exactly the failure mode that made the footer misleading (§1.1: four of the Accounts screen's own five keys never reach it). That test is what keeps this honest after the commit that ships it.

Scope: add HelpModal + its align: center middle rule in app.tcss:97; bind ?; set ENABLE_COMMAND_PALETTE = False; reword the two prose references to the palette; unit tests in the existing TUI suite. Nothing touches the engine, so the contract suite has nothing to see here. Docs to scrub in the same commit, per the backlog's working convention: tui-plan.md:324 (the ? help overlay ⬜, Textual command palette ⬜ line), backlog.md Phase 8, and a decisions.md entry for the palette removal — a deletion with a rationale is exactly the kind of call that has to survive a fresh clone.

Difference 2 — wording is the source's, not the drawing's. §6 invented New account / Edit selected / Down / Next page. Rather than keep a second copy of every label in the help code, the card reads Binding.tooltip and falls back to description — so a fuller phrase is set once, on the binding, and never reaches the footer.
