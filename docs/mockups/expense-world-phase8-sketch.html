expense world — phase 8 sketch · the deleted column · 2026-08-16
Phase 8 is the last open phase, and it is not a project — it is a drawer of ten leftovers from a review in July, explicitly marked “do these whenever”. Opening the drawer turned up something worth saying out loud first: three of the ten were already done. All three were fixed on 2026-07-10, in one commit, and nobody ever ticked them. Phase 7 caught a fourth item from that same commit and struck it — the other three were sitting right next to it and got missed.

What is actually wrong today: two of your lists lie to you. When you ask expense transactions list --include-deleted, deleted rows come back and sit in the table looking exactly like live ones. There is no column, no marker, nothing. Your accounts, categories, hashtags and reconciliations lists all have a Deleted column. Inbox and transactions do not. Pane 1 below is your real ledger proving it.

What this phase does: gives those two lists the same Deleted column the other four already have. Nothing else in the drawer gets opened — the test-suite sweep, the light theme and the help overlay stay parked, by your call.

Three things need your pick, marked in amber below: when the column shows up, where it sits, and one naming inconsistency that is sitting in the exact two lines of code this change has to edit. Nothing gets built until you choose.

2 · decision 1 — when should the column appear?
A · always
option
$ expense transactions list Title Description Amount Date Account Category Hashtags Deleted ----------- ----------- --------- ---------- --------- -------- -------- ------- Rent August — -1,800.00 2026-08-01 Interbank Housing #fixed no
real (rendered)The column is always there, exactly like accounts and the other three. Cost: every ordinary listing you ever run now carries a column that says no on every row — you will see it far more often than you will need it. Win: six lists, one rule, no surprises; the column set never changes shape.
B · only with the flag
option
$ expense transactions list Title Description Amount Date Account Category Hashtags ----------- ----------- --------- ---------- --------- -------- -------- Rent August — -1,800.00 2026-08-01 Interbank Housing #fixed $ … --include-deleted … Category Hashtags Deleted -------- -------- ------- Housing #fixed no Food — yes
real (rendered)You asked to see deleted rows, so you get the column that explains them; otherwise your table stays exactly as it is today. Cost: the two lists now behave differently from the other four, and the renderer needs to be told which flag you passed. Win: the column appears precisely when it is the thing you asked about.
C · only when a deleted row is there
option
$ … --include-deleted (nothing deleted) Title Description Amount Date Account Category Hashtags ----------- ----------- --------- ---------- --------- -------- -------- Rent August — -1,800.00 2026-08-01 Interbank Housing #fixed $ … --include-deleted (one is) … Category Hashtags Deleted -------- -------- ------- Housing #fixed no Food — yes
real (rendered)The quietest option: the column shows up only when it has something to say. Cost — and this is the one to think about: the same command gives you a different set of columns on Tuesday than it did on Monday, purely because of what is in the data. Win: you never see a column of no. (--json is unaffected by all three options — it always passes the engine body through whole, deleted_at included.)
