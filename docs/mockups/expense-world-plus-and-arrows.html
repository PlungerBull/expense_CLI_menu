Four rules that shape those numbers, all engine-side: (a) "current month" is the calendar month in your display_timezone, not a rolling 30 days. (b) Opening balances are excluded — the @Opening seed rows are where tracking starts, not money that moved, so they never inflate a month. (c) Every figure is home-currency, engine-converted; the CLI never does currency math. (d) If any transaction behind these totals has no exchange rate for its date, the whole cluster is replaced by 3 UNRATED rather than showing a figure that is quietly short.

§2a · Can the key be shift + +?  — no, and here is why

You asked whether shift + + avoids collisions. It cannot be bound, because a terminal has no way to send it. Two independent confirmations:

FactEvidence
A terminal sends characters, not key+modifier For printable keys the shift is already baked into the character — on a US layout the main-row + is shift + =. There is no second shift left to report. Textual says so in its own source: keys.py:323 — "If there is a separator, then it means a modifier (other than shift) is applied. Keys with modifiers don't come from printable keys."
Numpad + and main-row + are the same byte In normal keypad mode both send +. So one binding already covers the numpad key you asked for and the one over the =. Nothing extra to do.
Plain + collides with nothing — measured RENDERED probe, Textual 8.2.7: active_bindings on Home and on Transactions contains no plus entry; pressing + on the live app today does nothing at all. A probe app with a plus binding and a focused OptionList fires it cleanly. The list screens have no text input, so there is nothing for a + to be typed into.

Conclusion: bind plain +, displayed in the footer as + Add. It is free, it is unambiguous, and your numpad key hits it.

§2b · What + writes, and the Inbox gap

You asked how we write to the inbox right now. From the TUI: we do not. There is no way. The Inbox screen has exactly three actions — f filter, p promote, d delete — plus ⏎ to edit a draft that already exists. Creating one is flat-CLI only (expense inbox add --title "Lunch" --amount -1500). So this is a real hole in the TUI, and + is standing next to it.

C — + always posts a transaction. One key, one meaning, every screen.
Cost: the Inbox stays uncreatable from the TUI. The gap is left exactly as it is today.
HOME + → /transactions TRANSACTIONS + → /transactions INBOX + → /transactions creating a draft: still CLI-only
D — + creates in the list you are standing in. In the Inbox it makes a draft; elsewhere a transaction.
Cost: the same key writes to two different endpoints depending on where you are — the one thing you cannot tell by looking at the key.
HOME + → /transactions TRANSACTIONS + → /transactions INBOX + → /inbox creating a draft: + , inside the Inbox
H — + is always a transaction; n is "new row here". n New is already the convention on Accounts, Categories, Hashtags and Reconciliations (_base.py:396) — the Inbox is simply missing it.
Cost: two keys instead of one — but each means exactly one thing.
HOME + → /transactions TRANSACTIONS + → /transactions INBOX + → /transactions n → /inbox (new draft) creating a draft: n , like every other list

Recommended: H. It keeps + meaning one thing everywhere, and it closes the Inbox gap using the key the rest of the app already uses for exactly this. n is unbound on the Inbox today.

§4 · Arrows inside the edit form  — shift works, and it fixes a real bug

Yes, shift+↑ / shift+↓ can be bound — unlike shift++. Arrows are not printable characters, so the terminal sends a genuinely distinct sequence for them (CSI 1;2A / CSI 1;2B), which Textual maps to shift+up / shift+down (_ansi_sequences.py:234). Probed live with a focused Input: both fired, and neither typed anything into the bar.

And your instinct is pointing at a real defect. The form advertises ^↑ Prev field / ^↓ Next field in its footer — but on macOS, ⌃↑ is Mission Control and ⌃↓ is Application Windows, claimed by the OS before the terminal ever sees them. Unless you have turned those off in System Settings, the two field-navigation keys this form has always shown you have never worked. That is very likely why moving between fields felt wrong enough to write down.

Recommended: K. It is the closest thing to what you originally asked for — plain arrows move between fields — while still leaving the suggestion list a cursor on the three fields that have one, and it gives you one key (⇧↑↓) that means "field" with no exceptions anywhere. In both options ^↑ / ^↓ stay bound but stop being advertised, so nothing breaks for anyone whose Mission Control shortcuts are off. Unchanged either way: ⏎ saves the field and advances, ^s submits, read-only fields are skipped.
