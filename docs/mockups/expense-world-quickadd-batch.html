Quick-add — the one-line batch logger

One LOG bar. ↵ stages a line into the list below, ctrl+s writes the whole list, ↑/↓ pick a staged row back up to edit. Nothing reaches the engine until the save.

ANSI-only: default text, dim, blue accent, red/green for sign, reverse video for the picked row. No hex anywhere, so it reads the same on a light terminal.

v3 — what shipped, 2026-08-25

  • Panes 7 and 8 are redrawn to the four calls you made when phase 4 was planned. Pane 8 in particular changed shape: the interesting failure is not "nothing was written", it is half written — the drafts post after the batch, so the engine can die between them.
  • A saved row is done. It keeps its ✓, it is never re-sent, and it cannot be lifted back into the bar (correcting a written row is the edit form's job, which is why that door stayed open).
  • Pane 9's third answer is live — ctrl+s save first saves and then leaves, unless the save fails, in which case you stay where the error is readable.

v2 — what your review changed

  • Completion now rewrites the line (pane 3). Answering your @sig question: picking the USD account puts BCP Signature USD into the bar, because the text is the storage format.
  • Incomplete rows go to the Inbox (panes 5 and 7), with a goes to column so you see it before saving. Your call.
  • ctrl+arrows are gone. Plain ↑/↓ do double duty instead. Your instinct was right, for a sharper reason than you gave — see the note at the bottom.
  • Saving is one atomic call, not a loop (panes 7 and 8) — POST /transactions/batch already exists on the engine. This is the biggest change and it came out of your last question.

3 · …and ↵ rewrites the line

The answer: the completion edits the text. The token becomes @BCP Signature USD in the bar, so the line and the row can never disagree. This matters beyond tidiness — the line is the storage format when you pick a row back up to edit (pane 6), so a hidden binding behind stale text would be lost on the round trip. What you read is what gets saved.

8 · when only half of it is written

Routing at stage time means the engine has almost nothing left to refuse. A row is only sent to the ledger when it is already complete and not dated ahead; everything else was already addressed to the Inbox, which accepts it. So what is left is the engine being unreachable, logged out, or down — and because the drafts are posted after the batch, that can land between the two. The screen never claims more or less than what happened: rows that reached the engine keep their ✓ and are done, rows that did not keep their marker and carry the error, and ctrl+s re-sends only the rows without a tick. Nothing can be written twice — each row carries an id the client minted at stage time, so a row that did land replays as a 409, which is a tick, not a second copy. (Owner's call, 2026-08-25.) (A 422 — an account archived in another window since the list loaded — is isolated the same way: the screen re-posts row by row to name it, the fallback expense import has used since it shipped.)

grammar · what the parser reads
+ / − amount
-38.60  +2450  -1,311.97
A sign is what makes a number an amount, anywhere in the line. First sign wins — hoy +30 no -30 is +30. No sign, no amount: the number is just words in the title. Sign is literal, always.
$ account
$signature $bcp pen $nico
Matched against the account names already loaded; ↵ completes it to the full name, so multi-word names need no quotes. People are accounts here, same as everywhere.
@ category
@korakuen  @transporte
Same matching, same completion. Existing categories only — this screen never creates one.
# hashtag
#caja  #taxi #viajes
The one repeatable token — every # adds a tag.
// note
// pagué yo, dividir después
Everything after // is the description. Must follow a space, so a pasted https://… stays in the title.
when
hoy ayer 18/08/2026 2026/08/18
Words plus both slash orders — 4-digit-first is yyyy/mm/dd, otherwise dd/mm/yyyy, which cannot collide. Omitted = today. The resolved date is always echoed in words (Tue 18 Aug 2026) so a misread is visible before you stage.

two answers · the ones that needed more than a pane

Does the engine need work first? No.

Every call this screen makes already exists and is already exercised by this repo. POST /transactions/batch — atomic, client-supplied ids — is what expense import has posted xlsx rows through since it shipped; POST /inbox takes sparse drafts by design (only id is required); the three reference lists are already loaded by this very screen today. Nothing new, nothing changed, no migration.

One thing to pass to the engine coder — not a blocker. The spec says the batch endpoint “returns an array of any validation errors (with the index of the failing item)”. The importer found that it does not: apply.py carries the comment “an atomic-batch failure doesn't say which row” and works around it by re-posting one row per batch. So either the spec is describing an intention that was never built, or the shape drifted. It costs us nothing — the workaround is written and tested — but it is exactly the kind of contract gap this CLI exists to surface before web and iOS inherit it.

Why no ctrl+arrows — you were right to push back

Not because chords are unmappable: ctrl+s is already the submit key on every form in this app and works fine. It is ctrl+arrow specifically. macOS itself takes those before the terminal ever sees them — ctrl+↑ is Mission Control, ctrl+←/→ switch Spaces. Which means the ctrl+up / ctrl+down “prev/next field” bindings sitting in _form.py today are very likely dead keys on your machine, and no test covers them. Worth checking in any form and, if so, worth fixing separately from this screen.

Where this gets built — engine or client

The engine already did its half, and I only found it because you asked. POST /transactions/batch has existed since Step 6: an array of rows, one database transaction, all-or-nothing, errors reported per index. That is precisely what “save all” needs, and it turns pane 8 from “half-written, sort it out yourself” into “nothing was written.”

What stays client-side is the grammar, and I think that is right: completion has to run on every keystroke against reference lists the client already holds, so a round trip per character would be the wrong shape; and the precedent is already set — expense/dates.py is CLI-side date forgiveness by decision. The engine still validates every field it receives, so no correctness moves out of it. It lives in one module shared by the TUI and the flat expense log “…” command, per the one-copy rule.

The honest counter-argument: web and iOS would each rewrite the grammar. If you want all four clients to share one, that is an engine ask — a parse endpoint — and it is the engine coder's call, not mine. I would still build this one first, because the CLI's job is to find out whether the grammar is any good before three other clients inherit it.
